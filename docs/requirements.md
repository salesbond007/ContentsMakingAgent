# BONDAI MEDIA — CONTENT PIPELINE 要件定義ドラフト

コンテンツ制作自動化エージェント 要件定義書

BondAIメディアへ記事を自動投稿する、複数エージェント構成の制作パイプライン。
情報収集からmicroCMSへの公開までを、査読ゲートを挟んで自動化する。

- 作成日: 2026-09-04
- 対象: コンテンツ制作自動化（新規・別リポジトリ）
- 関連: BondAIMedia（サイト側・本パイプラインの投稿先）
- 投稿頻度: 1日3本

## 01 — 位置づけ

本ドキュメントは、BondAIメディア(サイト側リポジトリ)とは別に新規構築する「コンテンツ制作自動化エージェント」の要件を定義するものです。
サイト側リポジトリはmicroCMSを読む側、本パイプラインはmicroCMSに書く側という役割分担のため、実装は別リポジトリ・別セッションで進めます。
本書はその引き継ぎ用の仕様書として機能します。

対象読者：本パイプラインを実装するエンジニア／今後の要件レビューを行う社長。

## 02 — パイプライン全体像

1日1回のバッチ実行の中で、6つの工程が順番に走る。②〜④は記事1本ごとに繰り返され、1回の実行で3本分ループする。

1. 情報収集 — キーワード・ネタ出し
2. ライティング — 執筆・カテゴリ分類
3. 画像生成 — アイキャッチ生成
4. 査読・ファクトチェック — スコアリング・ゲート判定
5. 公開 — microCMSへ投稿
6. スケジューラ — GitHub Actions cron

## 03 — エージェント仕様

各エージェントの役割・入出力。実装は単一のNode.js(TypeScript)スクリプト内で、工程ごとに関数として分離する想定(重厚なマルチエージェントFWは不要な規模)。

### 01 情報収集エージェント

キーワードリストの消化を優先し、枯渇時のみAIが自動探索で補う。

- 入力: キーワード台帳(microCMS)／社内資料(Googleドライブ)／Web検索／競合サイトリスト／RSS
- 出力: 本日執筆する3件のお題(キーワード＋参考ソースURL)
- 優先順位: ①社内資料・登録済みキーワード → ②競合/業界サイト → ③トレンド探索・RSS

### 02 ライティングエージェント

記事本文の執筆に加え、カテゴリの自己分類・SEOメタ情報の生成まで担う。

- 入力: 工程01のお題・参考ソース
- 出力: title / excerpt / body / category(自己判定) / tags / seo.metaTitle / seo.metaDescription
- 備考: カテゴリのダブルチェックは行わない(査読エージェントは事実・表現のみ担当)

### 03 画像生成エージェント

記事内容からアイキャッチ画像を1枚生成。ブランドカラー(ワインレッド)を意識した固定スタイルプロンプトを付与。

- 入力: 記事タイトル・要約
- 出力: 画像ファイル＋altテキスト
- 使用API: OpenAI gpt-image-1(暫定)
- 失敗時: 記事全体は止めず、画像なしで下書き保存し要確認リストへ

### 04 査読・ファクトチェックエージェント

4観点でスコアリングし、自動公開/要確認/差し戻しをゲート判定する。詳細は「査読ゲート」参照。

- 入力: 工程02の本文・出典URL
- 出力: 4項目スコア＋合計点＋判定(自動公開/要確認/差し戻し)＋指摘コメント

### 05 公開エージェント

承認済みコンテンツをmicroCMSへ投稿する。掲載先(publishTargets)は原則「BondAIメディア」のみを自動設定。

- 入力: 査読ゲートを通過した記事一式
- 出力: microCMS articles への投稿(公開 or 下書き)
- 権限: 作成/更新のみのAPIキー(全権限キーは使わない)

### 06 スケジューラ

GitHub Actionsのcronで1日1回起動し、工程01〜05を3本分ループ実行。失敗時はSlack通知。

- 実行環境: GitHub Actions（サーバー常駐なし）
- 通知: Slack Incoming Webhook

## 05 — 査読ゲート：スコアリング

4観点を各25点、合計100点満点。BtoBメディアとして「断定・過剰な保証表現」を避ける方針を、リスク表現の項目で明示的に評価する。

- 事実確認(25点): 本文中の主張・数値が、出典URLの内容と整合しているか。出典が無い断定は減点。
- リスク表現(25点): 「必ず」「保証します」等の断定的表現、誇大な効果訴求が無いか。
- ブランド・トンマナ(25点): BondAIメディアの文体・語彙ガイドラインに沿っているか。
- 剽窃・重複(25点): 他サイトとの類似度、既存自社記事との重複が無いか。

判定:

- 80〜100点: 自動公開。公開エージェントがそのままmicroCMSへ投稿。
- 60〜79点: 下書き保存し、要確認キューへ。Slackに指摘コメント付きで通知、人が最終確認。
- 60点未満: 差し戻し。ライティングエージェントに再生成させるか、そのキーワードを破棄。

## 06 — データ・情報源の管理

- 使用済みキーワード台帳: microCMSに新規コンテンツ型 keywords を追加し、キーワード・使用日・紐づく記事IDを記録。情報収集エージェントは実行のたびにこの台帳を参照し、重複を避ける。
- 社内資料の参照: 共有Googleドライブの指定フォルダ(例：/BondAIメディア/ネタ元資料)を、読み取り専用のGoogleサービスアカウントで毎回スキャン。ドキュメント・PowerPointはテキスト抽出して情報収集エージェントの入力に含める。
- 掲載先の自動判定: 公開エージェントは publishTargets に常に「BondAIメディア」を設定する。コーポレートサイトへの追加掲載は自動判定せず、人が管理画面で個別に追記する運用とする(ブランドインパクトが大きいため)。

## 07 — 運用・監視

- Slack通知：実行開始／完了件数／要確認キュー発生／エラー発生の4イベントを通知。
- 統合管理ダッシュボードへの状態報告：実行結果(成功/失敗件数・査読スコア分布)を、ダッシュボード側の仕様確定後にAPI連携する。
- 監査ログ：GitHub Actionsの実行ログを一次ログとし、「誰が(どのエージェントが)・何を・いつ投稿したか」をmicroCMSの更新履歴と突き合わせられるようにする。
- リトライ：LLM呼び出しの一時的エラーは1回リトライ。2回失敗した工程はその記事をスキップし、次のキーワードへ進む(1本の失敗で全体を止めない)。

## 08 — 技術スタック(暫定)

| 領域 | 選定 | 理由 |
| --- | --- | --- |
| 実行環境 | GitHub Actions (cron) | サーバー常駐不要・低コスト・シークレット管理が容易 |
| 言語 | Node.js / TypeScript | サイト側リポジトリと統一、型でmicroCMSスキーマとの整合を取りやすい |
| 文章生成・査読 | Claude API | 要件定義・査読基準との相性、長文生成の安定性 |
| 画像生成 | OpenAI gpt-image-1 | プロンプト再現性、スタイル固定のしやすさ |
| データ保存先 | microCMS | サイト側と共通のCMS。articles / keywords を利用 |
| 通知 | Slack Incoming Webhook | 導入コストが低く即時性がある |
